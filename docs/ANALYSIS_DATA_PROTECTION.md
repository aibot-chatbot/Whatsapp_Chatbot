# Analysis：业务记录与数据保护

**当前状态：本地实现和测试已完成，尚未迁移或部署到生产。以下入口在分项验证并开启功能后生效。**

## 商家怎样使用

1. 打开 Bot，在 Conversations 下方进入 Analysis。只有当前有效的 owner/admin 可访问报告接口。
2. 上传业务文档后，系统沿用行业识别建议；商家在 Bot instructions 确认行业。每个 Bot 保留自己的角色、语气与业务资料。
3. 输入报告要求，例如“生成餐厅上个月的预约申请与待跟进报告”。后台保存任务、锁定数据快照，再生成分析及 PDF、Excel；下载时重新校验权限。
4. 如需持续记录客户请求，主动开启 Record customer requests。它分析新收到的客户文本，使用该 Bot 的模型及 AI 额度。关闭后停止新的分析。
5. 周报/月报默认关闭。开启后按吉隆坡时区统计上一完整期间；停机恢复最多补最近一期。

试听场次由商家在 Analysis 管理。网页客人使用聊天里的试听预约入口；Telegram 客人发送 `/trial 参加者姓名`，选择实际场次并确认后取得预约编号。提醒仅支持已连接的 Telegram 渠道，需要客人同意及生产提醒功能启用；网页渠道不会显示为已启用自动提醒。

## 客人的数据存在哪里

| 数据 | 位置 | 用途 |
|---|---|---|
| 原始客户消息 | Supabase `messages`，关联 `conversations` | 可信渠道或网页会话的原始证据 |
| 请求及业务结果 | Supabase `business_events` | 公司、Bot、会话、动作、状态、消息证据与幂等标识 |
| 试听参加者、场次、确认和预约 | Supabase `tuition_participants`、`tuition_sessions`、`tuition_confirmations`、`tuition_bookings` | 参加者绑定可信会话；确认有效期、场次版本和容量由数据库原子检查 |
| 报告任务与固定快照 | Supabase `analysis_reports` | 三种报告格式使用同一份事实；模型只添加分析 |
| 模型调用状态 | Supabase `analysis_model_steps` / 观察任务状态 | 防止旧 Worker 覆盖、新 Worker 重复收费 |
| 报告文件 | 私有 R2 `reports/`，本地开发使用私有目录 | 不使用公开 `/media/` 路径；通过鉴权接口下载 |

“想预约”“提交报名申请”与“已确认预约”不同。模型只能记录意图或申请；真实业务服务成功后才能写入确认结果。未连接的餐厅/诊所预约系统不会产生假的成功编号。首版正式预约能力限定为补习试听，不包含正式报名或收学费。

## 已实施的边界

- 身份与公司从当前数据库用户及可信会话推导，不接受前端提交的公司身份。
- 数据库 RPC 复核公司、Bot、会话、证据消息关系；即使没有员工 actor 也检查租户。
- Analysis 表启用 RLS，浏览器 anon/authenticated 角色不能直接读写。服务器经受限函数写入；报告生成、导出与下载重新检查权限和套餐。
- 模型不接收 SQL 执行入口，不决定权限，也不能用 `confirmed=true` 代替客户确认。
- 确认的医疗行业仅使用结构化行政记录；自由文本病历、对话内容和文档正文不进入报告模型。医疗行业文件总结需先建立经批准的行政资料来源。
- 非医疗运营报告可在私有快照保存最多 100 条客户文本样本（每条最多 600 字符、总计 12,000 字符），保留消息来源编号用于核查。系统清理可识别的联系方式格式；这不等同于完整匿名化。样本不足、截断或读取失败会明确说明，不能据此声称覆盖全部客户问题。
- 文件路径由服务器生成，租约版本隔离旧 Worker，校验内容哈希，下载响应禁止公共缓存。
- 不明的供应商调用结果进入待核查；通知或文件生成重试不会重新调用已成功的模型步骤。
- 人工回复使用明确的员工或消息来源证据；旧非 AI 消息若无法确定作者，单独列为归属不明。自动提醒不计为人工回复。

## 发布前仍需证明

本文描述代码中的边界，不等于生产验证。迁移、云端 Worker、备份恢复、告警和实际渠道提醒必须分别完成验证后开启。当前没有新增自动删除周期；现有消息保留政策仍适用，报告文件生命周期须在生产发布记录中明确。
