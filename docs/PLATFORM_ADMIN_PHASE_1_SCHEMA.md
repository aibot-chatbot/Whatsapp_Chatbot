# Platform Admin Phase 1: Schema Verification and Migration Design

## Status and scope

**Verified complete in staging; not deployed to production.** Migrations 023,
024, and 025 were applied successfully in staging. Their tables, identity
columns, foreign keys, checks, indexes, ownership, sequence privileges, RLS,
policies, effective privileges, and absence of triggers were verified.

Production deployment remains blocked by the approval gates recorded in the
Phase 1.5 security and staging report. No platform-admin bootstrap data, APIs,
frontend pages, or authentication middleware have been created.

Historical clarification: this phase record describes migrations 023 through
025 at the time they were designed and verified. Migration 026 later implemented
Option C, a database trigger that rejects UPDATE and DELETE on
`platform_admin_audit_events`; use the Phase 4 production-readiness document for
the current append-only posture.

This phase does not change production data or alter Flow Builder or Broadcast.

## Current behavior found

- Authentication issues application JWTs with `user_id`, `company_id`, and the
  tenant `role`. Existing authorization accepts only `owner`, `admin`, and
  `member` semantics.
- New company accounts are currently created as tenant `admin`; team management
  accepts only `admin` or `member`. No platform-admin authorization exists.
- The existing `/api/admin/billing` routes are company-scoped tenant-admin
  routes. Their module explicitly says cross-company platform administration is
  deferred.
- Sensitive tenant billing actions currently use structured application logs,
  not a database audit-event table.
- Repository code writes UTC ISO timestamps for `created_at` and `updated_at`.
  Versioned SQL uses `TIMESTAMPTZ NOT NULL DEFAULT NOW()`. No repository migration
  establishes an automatic `updated_at` trigger.

## Relevant schema evidence

| Object | Verified live-schema finding | Migration impact |
|---|---|---|
| `users.id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY`, primary key | Both user references use compatible BIGINT FKs |
| `companies.id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY`, primary key | Confirms the project identity-column convention |
| `users.company_id` | BIGINT FK to `companies.id`, `ON UPDATE CASCADE ON DELETE CASCADE` | Compatible, but company deletion can reach the new RESTRICT user FK; see risks |
| `users.role` | No CHECK constraint and no constraint or index mentions the column | Migration does not alter the column or add `platform_admin` |
| Timestamp triggers | No timestamp-maintenance triggers on inspected tables | `updated_at` remains application-managed; no trigger is added |
| Generated IDs | Existing generated IDs use PostgreSQL identity columns | Both new IDs use `BIGINT GENERATED BY DEFAULT AS IDENTITY` |

The complete reported constraint and FK results are compatible with the two new
FKs: both reference the BIGINT primary key `public.users(id)`. `ON UPDATE
RESTRICT` is safe for identity primary keys, and the requested deletion rules
are explicit rather than inherited from `users.company_id`.

The available numbered SQL begins at `003`; it is not a complete schema history.
Files `006` through `018` are the primary relevant migration/RPC evidence, with
`014_billing_notifications.sql` supplying the closest table-style convention
for `BIGINT`, `TIMESTAMPTZ`, `JSONB`, indexes, comments, grants, and PUBLIC
revocation. The verified live schema supersedes its older BIGSERIAL convention
for new generated IDs.

## Timestamp convention

Use `TIMESTAMPTZ NOT NULL DEFAULT NOW()` for both creation and mutable-row update
timestamps. Live inspection confirmed that no timestamp-maintenance trigger is
present, so application code must explicitly set `updated_at` on every update.
Audit events are append-only and need only `created_at`.

## Finalized migrations verified in staging only

1. `data/023_create_platform_admin_users.sql`
2. `data/024_create_platform_admin_audit_events.sql`
3. `data/025_enable_platform_admin_rls.sql`

All three were applied and verified successfully in staging. They remain
unapplied in production. Phase 1.5 corrected the grant sequence so `service_role`
is revoked before the intended minimum privileges are granted; staging verified
the resulting effective privilege matrix.

Migration 025 enables non-forced RLS on both tables. It creates no policy for
`anon` or `authenticated`; it creates service-role SELECT/INSERT/UPDATE policies
for `platform_admin_users` and SELECT/INSERT policies for
`platform_admin_audit_events`. Staging confirmed `service_role` has `BYPASSRLS`,
so these policies do not constrain that role.

### `platform_admin_users`

- BIGINT identity primary key generated by default
- unique, required BIGINT `user_id` referencing `users.id`
- required `is_active`, default true
- required TIMESTAMPTZ `created_at` and `updated_at`, default now
- nullable BIGINT `created_by_user_id` referencing `users.id`
- table and column comments explicitly separate platform admins from tenant roles

Recommended deletion behavior is `RESTRICT` for `user_id`: platform-admin users
should be deactivated rather than deleted. Bootstrap rows may have a null creator;
later deletion of a creator uses `SET NULL` without removing the provisioned
administrator or its history.

### `platform_admin_audit_events`

- BIGINT identity primary key generated by default
- required BIGINT `platform_admin_user_id`
- required non-blank `action` and `resource_type`
- nullable TEXT `resource_id` to support heterogeneous BIGINT, UUID, and external
  identifiers
- required JSON object `metadata`, default `{}`
- required TIMESTAMPTZ `created_at`, default now

The actor FK uses `RESTRICT`, retaining audit attribution and reinforcing the
deactivate-not-delete model. Recommended indexes cover actor timelines and
resource timelines. An action/time index can be added later if a concrete query
requires it; an `is_active`-only index is not useful for the expected small
administrator allowlist.

`ip_address` is deliberately omitted. No persisted IP-address convention exists
in the repository. If one is approved, use PostgreSQL `INET`, define trusted
proxy/header handling in the application, and decide whether privacy retention
requires truncation or expiry.

## Bootstrap procedure still required

The first platform administrator cannot be safely self-provisioned by application
code that does not yet exist. Before deployment, approve a one-time runbook that:

1. Selects a dedicated, verified internal `users` row belonging to a protected
   internal company that will not be tenant-deleted.
2. Confirms the user is active and uniquely identified by both ID and email.
3. Inserts one `platform_admin_users` row with `created_by_user_id = NULL`.
4. Records the operator, approval ticket, timestamp, selected user ID, and result
   outside the new database audit table for this bootstrap event.
5. Verifies the inserted mapping without changing `users.role`.
6. Defines emergency revocation as `is_active = FALSE` with an explicit
   application-managed `updated_at` value.

The exact bootstrap INSERT is intentionally not included until the approving
operator supplies and independently verifies the target user ID.

```sql
SELECT
    to_regclass('public.platform_admin_users') AS platform_admin_users,
    to_regclass('public.platform_admin_audit_events') AS platform_admin_audit_events;

SELECT rolname
FROM pg_roles
WHERE rolname IN ('anon', 'authenticated', 'service_role')
ORDER BY rolname;

SELECT
    n.nspname AS schema_name,
    c.relname AS table_name,
    c.relrowsecurity AS rls_enabled,
    c.relforcerowsecurity AS rls_forced,
    pg_get_userbyid(c.relowner) AS table_owner
FROM pg_class AS c
JOIN pg_namespace AS n ON n.oid = c.relnamespace
WHERE n.nspname = 'public'
  AND c.relname IN ('users', 'companies')
  AND c.relkind IN ('r', 'p')
ORDER BY c.relname;

SELECT
    defaclrole::regrole AS owner_role,
    COALESCE(defaclnamespace::regnamespace::text, 'all schemas') AS schema_name,
    defaclobjtype AS object_type,
    defaclacl AS default_acl
FROM pg_default_acl
ORDER BY owner_role::text, schema_name, object_type;
```

## Risks

- Reusing `users.role = 'admin'` for platform access would create a cross-tenant
  privilege escalation. Platform authorization must require an active row in
  `platform_admin_users` independently of tenant role.
- `CREATE TABLE IF NOT EXISTS` is rerunnable but does not repair a conflicting,
  partially created table. Deployment validation should compare the catalog to
  the approved definition before and after migration.
- Service-role access bypasses many RLS configurations; future repositories and
  APIs must enforce the separate platform-admin check server-side.
- The `users.company_id ON DELETE CASCADE` path will be stopped by the platform
  admin `user_id ON DELETE RESTRICT` FK. Use a protected internal company and a
  reviewed lifecycle process rather than weakening audit-preserving deletion.
- Mutable or deletable audit events weaken accountability. The migration grants no
  UPDATE or DELETE on the audit table, but database owners still require an
  operational retention policy.
- Metadata can leak secrets or personal data unless Phase 2 uses an explicit
  allowlist and redaction rules.
