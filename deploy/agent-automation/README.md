## Processes and persistent state

| Process | Singapore machine | Persistence | Permitted work |
| --- | --- | --- | --- |
| Langflow 1.12.2 base profile | shared-cpu-2x, 2 GB, one always-running machine | SQLite in a 2 GB `langflow_data` volume | Reviewed flow forwards only persisted `run_id` / `step_id` to Flask |
| n8n 2.39.10 | shared-cpu-1x, 1 GB, one always-running machine | Dedicated PostgreSQL login and private `agent_n8n` schema; no volume; stable encryption key | Periodic authenticated schedule tick and health pings; no customer-message delivery |
| Analysis worker | shared-cpu-1x, 2 GB, one always-running machine | Supabase queue/report/step rows; private R2 artifacts (`DOCUMENT_STORAGE_BACKEND=r2`) | Alternating report, observation and optional reminder claims, concurrency one |

Every public `http_service` sets `auto_stop_machines = "off"`, so Fly never auto-stops these machines. Langflow and the worker listen on `::` and are reached as `<app>.internal`. The n8n editor is public HTTPS (owner decision 2026-09-24: `fly proxy` from the operator PC stalls on uploads over ~8 KB). Langflow's editor and API stay private on 7860 behind `fly proxy`; its only public surface is Langflow's built-in MCP endpoint `https://aibot-agent-langflow-my.fly.dev/api/v1/agentic/mcp` on a second listener (8080), where the entrypoint returns 404 for every other path and rewrites Host so the MCP tools' loopback REST calls stay on the private listener (owner decision 2026-09-26). Flask's gunicorn binds IPv4 only, so `.internal` cannot reach it: n8n and Langflow call `https://aibot-chatbot-my.fly.dev`. Do not expose the Langflow editor or widen that path allowlist. A stopped singleton causes delay; this package does not promise high availability or exactly-once external delivery.

Langflow does not start through `langflow run`: that command probes the port over IPv4 and hands gunicorn `":::7860"`, which it parses as an empty port. The image entrypoint (inline in `langflow.Dockerfile`) starts as root, takes ownership of the root-owned Fly volume for UID 1000, drops to that user and runs `uvicorn --factory langflow.main:setup_app --host ::` with access logs off. n8n runs without a volume because a root-owned mount would break its `node` user and all its state is in PostgreSQL.

The worker entrypoint is `python analysis_worker.py`. It never calls `create_app` or imports `wsgi`, and forcibly disables inherited billing, ingest and Wasender background flags. It still imports existing application modules and uses the tested Flask image's dependencies. Its memory usage must be measured during the isolated deployment smoke; it has not been benchmarked here.

**Developer sandbox.** Other developers use `aibot-agent-langflow-dev` (`https://aibot-agent-langflow-dev.fly.dev`, `langflow-dev.fly.toml`), never production Langflow: any Langflow login can run custom Python on its server (`LANGFLOW_ALLOW_CUSTOM_COMPONENTS` defaults to true and is global), and production holds `AGENT_INTERNAL_TOKEN`. The sandbox has a public editor, its own accounts (sign-ups stay inactive until the admin activates them), no production secrets, its own Fly private network (`fly apps create --network langflow-dev`) and auto-stop when idle. Its admin login is in `%USERPROFILE%\.omnexa-secrets\langflow-dev.env`. Promote a finished flow by exporting its JSON and importing it into production through the `langflow-omnexa` MCP after review.

## Failure behavior and monitoring

Atomic claims use `FOR UPDATE SKIP LOCKED`. Each attempt gets a fresh UUID lease; renewal, final publication and failure settlement require that unexpired lease. Report, observation and reminder kinds are isolated from n8n. Safe failures retry at 15/30 seconds up to three attempts by default; an in-flight provider marker on failure or expiry becomes `needs_review` and is not automatically replayed. If analysis fails after its numeric snapshot was frozen, a partial facts-only report can be published with an explicit AI/billing-review limitation; the queue and provider marker still require review. Final report publication and queue settlement share one database transaction. Frozen snapshots and successful model-step outputs are reused on safe retries.

The worker's health becomes degraded after a failed DB poll or no completed poll for 15 minutes. Fly restarts a process that exits; a failed health check **does not by itself restart a stuck process**. Langflow and n8n readiness only proves process/database readiness, not successful scheduled work. An external heartbeat monitor with a tested alert is a release gate.

Healthchecks.io free tier (no cost), driven by `n8n-health-pings.json`:

1. Create a Healthchecks.io project, copy its **ping key**, and add checks with these slugs: `aibot-n8n` (period 5 min, grace 5 min), `aibot-agent-worker` (period 5 min, grace 20 min, longer than the worker's own 15-minute degraded threshold) and `aibot-agent-langflow` (period 5 min, grace 10 min). Connect an email or Telegram integration and send a test notification.
2. In n8n, replace `REPLACE_HC_PING_KEY` in the imported health workflow's URLs. Keep the real key out of Git. A leaked key lets someone fake pings, which could hide an outage; rotate it in Healthchecks.io if exposed.
3. Every 5 minutes the workflow pings `aibot-n8n`, then GETs worker `/healthz` and Langflow `/health_check` over `.internal`. A 200 pings the matching check and any error or 503 pings its `/fail` URL. If n8n itself stops, all three checks go overdue.
4. In each tick workflow's Settings, choose this workflow as the **Error workflow**. A failed tick then pings `aibot-n8n/fail` until the next alive ping. Activate the health workflow before any tick.
5. Add a free external HTTP monitor on `https://aibot-chatbot-my.fly.dev/` for Flask, and a spend alert in the Fly billing dashboard.

Not yet covered: a silently deactivated tick (no success ping, because the tests pin the tick workflows to two nodes), oldest due job older than 5 minutes, expired leases, `needs_review` and exhausted attempts. The isolated `agent_n8n` role cannot read application tables, so these need a bearer-protected Flask status endpoint, which does not exist yet.

Do not log report text, document contents, customer text or bearer tokens. IDs/status/error codes suffice. Review `needs_review` using the provider's authoritative outcome before authorizing another paid step. Never reset `external_effect_started`, lease tokens or model-step state merely to make the queue green.

## Restart, backup and rollback

- Restart drill: stop the worker during an unstarted task and verify bounded reclaim; separately use a mocked/isolated in-flight model step and verify `needs_review`. Restart n8n and confirm workflows/credentials survive. Restart Langflow and confirm the imported flow and auth survive. These drills have not been run against deployed machines.
- Back up Langflow SQLite with SQLite's online backup API or a stopped-machine volume snapshot, plus reviewed flow JSON, before upgrades. Fly volume snapshots are additional recovery points, not the sole backup. Retain encrypted off-machine backups and prove a restore into an isolated app.
- Back up the private n8n PostgreSQL schema with `pg_dump --schema=agent_n8n` using the approved backup account; encrypt exports. Keep `N8N_ENCRYPTION_KEY` separately backed up or restored credentials cannot be decrypted. Existing Supabase backup coverage/retention must be verified, not assumed. n8n has no volume; its container filesystem is disposable.
- Pause n8n ticks, stop worker claims and disable new Analysis requests before rollback. Preserve leases and uncertain outcomes. Redeploy previous recorded image digests only if schema compatibility is established. An n8n/Langflow metadata downgrade may require restoring its pre-upgrade database/volume; changing the image alone is insufficient. Do not down-migrate or delete tenant report data as routine rollback.
- Flask may roll back independently only while new features are disabled and old code remains compatible with additive migrations. Previously produced R2 files remain private. An old worker's versioned uploads cannot overwrite the winning lease's files.
